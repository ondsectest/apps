Personal dictionary word length is validated only on the client

Wispr Flow Pro desktop (macOS, Electron). The Add word field caps input at 60 characters, but the Dictionary Personal API accepts and stores a far longer value when the client cap is bypassed.

Platform: Wispr Flow Desktop, macOS Build: WisprFlow/1.6.1337, Electron 43.8.3 Area: Settings, Dictionary, Personal Type: Client-side-only validation CWE-1284 / CWE-20
What happens: the desktop UI stops you at 60 characters, so it looks validated. Replaying the add-word request with a 100-character word returns HTTP 200 and the server stores all 100 characters. The limit is cosmetic.
Expected: the server enforces the same length rule as the client. An over-limit word is rejected with a clear validation error, and no record is created. Client and server agree.

! Root cause: the 60-character limit lives only in the desktop app. The Dictionary Personal API performs no length check, so any client that skips the UI (an intercepting proxy, a scripted call, a modified build) can write oversized values.
  • Oversized dictionary entries can bloat storage and sync payloads for that account.
  • Unbounded input is a classic lead-in to further issues: truncation mismatches, UI layout breakage, and downstream parsing or display bugs wherever the word is rendered.
  • If length is the only thing unchecked, it is worth confirming the server also validates content, type, and the replacement fields the same way.

Step 1 — Server enforces the same limit

POST /api/v1/dictionary/personal (word set to 100 characters)Response
HTTP/2 422 Unprocessable Entity
Content-Type: application/json

{
  "error": "validation_error",
  "field": "word",
  "message": "Word must be 60 characters or fewer.",
  "max_length": 60,
  "received_length": 100
}
✓ Validate on both sides. Keep the field cap for a good typing experience, and make the server the source of truth. Reject over-limit input with a specific, actionable message and create no record.
  • Define the length limit once (shared constant or schema) and apply it to the client input and the API contract so they cannot drift apart.
  • Return a structured validation error with the field, the limit, and what was received, so clients can surface a helpful message.
  • Apply the same server-side rule across every write field here (word, replacement) and reuse it on other forms in the app for consistency.
  • Add an API test that posts an over-limit value directly, so the protection cannot regress unnoticed if the UI changes.
i Tested on the researcher's own account and traffic only, using a locally trusted proxy. No other users or data were involved.
