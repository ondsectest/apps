A snippet can be created with no expansion by flipping is_snippet

Wispr Flow Pro desktop (macOS). The UI will not let you save a snippet without an expansion. Changing is_snippet from false to true on a dictionary add request creates a snippet that has a name and no expansion, which the business logic forbids.

Platform: Wispr Flow Desktop, macOS Endpoint: POST /api/v1/dictionary/personal Area: Dictionary, Snippets Type: Business logic bypass CWE-840 / CWE-20 / CWE-602
What happens: in the Add snippet form, Save is disabled until an expansion is entered. But a dictionary word has no expansion, so flipping is_snippet to true on the add-word request (with replacement: null) creates a snippet with a name and no expansion. The server accepts it, breaking the rule the UI enforces.
Expected: the server enforces the same rule as the UI. When is_snippet is true, a non-empty replacement is required, and a request without one is rejected. The client and server agree on what a valid snippet is.

! Root cause: the rule that a snippet must have an expansion is enforced only in the UI (Save stays disabled). The API does not require replacement when is_snippet is true, so a crafted request creates a snippet the product considers invalid.
  • Business logic enforced only on the client can be bypassed by editing the request directly.
  • An expansion-less snippet is a broken state: triggering it produces nothing, and any view or sync that assumes a snippet always has an expansion may misbehave.
  • Signals that other field relationships (for example a snippet name being present) may also be unenforced server-side, worth confirming.

Step 1 — Server enforces the business rule

POST /api/v1/dictionary/personal (is_snippet true, replacement null)Response
HTTP/2 422 Unprocessable Entity
Content-Type: application/json

{
  "error": "validation_error",
  "field": "replacement",
  "message": "A snippet requires a non-empty expansion."
}
✓ Enforce the rule where it is authoritative. Validate on the server that a snippet (is_snippet true) has a non-empty replacement, mirroring the UI. Reject the request and create no record otherwise.
  • Define the "a snippet needs an expansion" rule once and apply it to both the form and the API contract.
  • Return a structured validation error naming the field and the rule, so clients can show a clear message.
  • Review related field relationships (name required, type consistency) and enforce them server-side too.
  • Add an API test that posts is_snippet true with an empty expansion and expects a rejection.
