Snippet form saves despite a client-side validation error

Wispr Flow Pro desktop (macOS). The Edit snippet expansion field shows a red over-limit error at 4853 / 4000 characters, but Save changes stays active, the save succeeds, and a confirmation appears. The error is shown but not enforced.

Platform: Wispr Flow Desktop, macOS Area: Settings, Dictionary, Snippets, Edit Field: Expansion, max 4000 Type: Error shown, not enforced CWE-20 / CWE-1284 / CWE-1173
What happens: the expansion counter turns red at 4853 / 4000 and the field shows an error border, yet Save changes is still clickable. Saving succeeds and the snippet is updated, so the validation error does not actually block the save.
Expected: while the expansion is over the limit, Save changes is disabled and a clear message says how much to remove. The form cannot be saved in an invalid state, and the server rejects an over-limit value as a backstop.

  • The validation error is displayed but not wired to the submit action, so the limit is advisory, not enforced.
  • Consistent with the other dictionary and snippet findings, the server also appears to accept the over-limit value, so there is no backstop either.
  • A user can save content the product's own rules forbid without realising the "error" did nothing.
  • Oversized expansions can bloat storage and sync payloads and break any view that assumes the 4000-character bound.

  • Tie the validation state to the submit control: while any field is invalid, the save action is disabled.
  • Show a specific, actionable message (how many characters to remove), not just a red counter.
  • Enforce the same limit on the server and reject over-limit values, so a bypassed client cannot save them.
  • Apply the pattern consistently across the snippet name, the expansion, and other forms.
