Snippet name length is validated only on the client

Wispr Flow Pro desktop (macOS, Electron). The snippet name field caps input at 60 characters, but the snippets API accepts and stores a longer name when the client cap is bypassed. A boundary value violation.

Platform: Wispr Flow Desktop, macOS Build: WisprFlow/1.6.1337, Electron 43.8.3 Area: Settings, Dictionary, Snippets Type: Client-side-only validation CWE-1284 / CWE-20 / CWE-602
What happens: the desktop UI stops the snippet name at 60 characters, so the limit looks enforced. Replaying the add-snippet request with a 100-character name returns HTTP 200 and the server stores the full name. The boundary is enforced only on the client.
Expected: the server enforces the same 60-character limit on the snippet name. An over-limit name is rejected with a clear validation error, and no snippet is created. Client and server agree on the boundary.

Root cause: the 60-character snippet name limit lives only in the desktop app. The snippets API performs no length check, so any client that skips the UI (an intercepting proxy, a scripted call, a modified build) can write oversized names. This is a boundary value violation: the documented maximum is not enforced where it is authoritative.
  • Oversized snippet names can bloat storage and sync payloads, and break any UI that assumes a 60-character bound.
  • Unvalidated input is a common lead-in to further issues: truncation mismatches, layout breakage, and parsing or display bugs wherever the snippet name is shown or matched.
  • Worth confirming the server also bounds the expansion field and validates content and type, not just the name.

Step 1 — Server enforces the same boundary

POST /api/v1/dictionary/personal (snippet name set to 100 characters)Response
HTTP/2 422 Unprocessable Entity
Content-Type: application/json

{
  "error": "validation_error",
  "field": "word",
  "message": "Snippet name must be 60 characters or fewer.",
  "max_length": 60,
  "received_length": 100
}
✓ Validate on both sides. Keep the field cap for a good typing experience, and make the server the source of truth for the boundary. Reject over-limit names with a specific, actionable message and create no snippet.
  • Define the snippet name limit once (shared constant or schema) and apply it to the client input and the API contract so they cannot drift apart.
  • Return a structured validation error with the field, the limit, and what was received, so clients can surface a helpful message.
  • Bound the expansion field on the server too, and reuse the same validation pattern on other forms in the app for consistency.
  • Add an API test that posts an over-limit snippet name directly, so the boundary cannot regress unnoticed if the UI changes.
